# P2 DIGITAL FORTRESS — integration contract and implementation plan

**DRAFT — NO GO.** This is a design, not an implementation, security approval, audit report, release, or authorization to contact a target. Keep the normal audit endpoint disabled until every gate below is independently closed. No public site or service was contacted to prepare this plan.

## 1. Basis and present boundary

The revised JLV mandate calls for an authorized, low-impact configuration audit and controlled detection, a local bilingual printable full report and cached GHSA comparison, but does not authorize a third-party audit without separate target-specific consent. `DIGITAL_FORTRESS_CONTRACT.md` is a draft. The integration clone was inspected on branch `p2/digital-fortress`, base `82fc9c4f8b05e0a4c4536e5329be8fef0db27a6c`, with pre-existing uncommitted work. It must not be confused with a released build.

`OUT/backend-integration.json` reports the guarded `POST /api/fortress/audit` intentionally returns 503 without reading the body or constructing a transport. `fortress_checks.py` is pure and offline, consumes caller-attested facts, and unconditionally makes `version` indeterminate. `OUT/frontend-fix.json` reports a mock-tested privacy-reduced summary; `fortressReport.ts` retains only bounded request count and recognized id/status/severity and explicitly says it is not a full report. `OUT/transport-final-review.json` records a NO GO with seven blockers. Some transport code has since changed from line-specific review observations; code appearance is not independent closure. Re-review the exact integration tree and rerun adversarial cases before changing this decision. Previous test results in OUT are historical, not tests run for this document.

**Not implemented or proven here:** production audit orchestration and validated fact producer; complete bilingual report; safe reproduction metadata; GHSA component matcher; full endpoint request/schema and response integration; independent end-to-end privacy and production-peer proofs. A TLS lab that fabricates `getpeername()` is not real public-peer provenance. No overall P2 completion is implied.

## 2. Activation gate and normal endpoint sequence (proposed)

1. Independently resolve, retest, and review all seven `transport-final-review.json` blockers: HTTP status/Retry-After and negative proof; WAF/rate signals plus atomic stop/concurrency; ambiguous routes and query keys; causal baseline/control for probes; malformed/combined cookie handling; privacy/raw boundary; and SSRF/actual peer/production dependency injection. Explicitly retain uncertainty around unknown WAF signals, blocking DNS and cooperative deadlines. Document exact candidate identity and review evidence; fixes after the review need fresh verification, not an assumed pass.
2. Keep the existing local Host guard, exact singleton allowed Origin and singleton `X-Sentinel-Request: sync`, no endpoint query, manual POST only. Enforce JSON content type, bounded streaming body before parsing, reject duplicate JSON keys, unknown fields, invalid types and invalid authorization before DNS or any transport construction. Apply error and log redaction. Neither GET, startup, language change nor report retrieval can start an audit. Local guards are not authentication nor a substitute for explicit authorization.
3. Validate and freeze an immutable scope and probe approvals. Instantiate one audit-owned policy/service and one shared serialized budget/stop latch, including redirects, baselines and all probes. Production construction must not accept API-controlled scope objects, resolver/socket/TLS overrides, test transports, private-IP bypass, arbitrary headers or proxy configuration. Unit injection belongs only to trusted test code; a separate inaccessible lab harness is required for real loopback fixtures.
4. The service executes only approved bounded observations through the safe derived-facts boundary; no `request()` raw `Response` into the rule layer, persistence, API, UI or logs. A halt prevents every next DNS/send, including queued requests. Produce one typed fact set **per route index and method/probe**, not an invented aggregate. Read a consistent GHSA cache snapshot locally; never call `fetch`, POST, client, or third-party service from the audit. Map only completed, fully attributable observations to rules; mark all remaining checks indeterminate. Construct validated structured results, localize via fixed keys, and only then render a report. Publish after output validation and any chosen transaction commit/readback. Cancel/abort must not resurrect stale results or trigger retries.
5. Proposed service integration is **only through the normal local endpoint after gate 1**. Preserve the existing 503 until then. If persistence is chosen, use additive project-local tables, an explicit transaction and commit confirmation, no legacy row changes or raw responses; a read-only result path must never initiate collection. If result storage is not implemented, label results ephemeral and do not promise later retrieval. No new listener, cloud component, service, scheduler or automatic scanner.

## 3. Request and settings contract

Existing frontend request DTO: `{target, additional_urls, level, authorized, parameters}`; `parameters[] = {url, name, kind}` where `kind` is `reflection` or `redirect`. This is not yet a validated backend contract. Define a strict versioned schema and reject extra fields, duplicate keys, `authorized` other than literal `true`, non-string URLs/names, unknown level/kind, duplicate routes or ambiguous equivalent parameter names. `target` is one HTTP(S) URL; `additional_urls` at most three exact same-origin manually approved URLs. `level` is `standard` or `deep`; standard requires an empty parameters list; deep parameters must name an exact submitted route and unique explicitly authorized key and purpose. Set an explicit finite maximum parameter count (candidate: 16 per audit, subject to request budget) and enforce consistently in API, UI and scheduler. Confirmation must cover ownership/authority, scope, level, individual test parameters and routes safe for GET/HEAD/OPTIONS; changing any input invalidates authorization, pending response and prior result. The user must not submit secrets or personal data in paths, parameter names or values; reject URL query strings in this initial contract (current UI already strips/rejects them). Tests add only fixed internal inert probe values to approved keys. Do not silently repair malformed inputs.

Server-owned settings, not user bypasses: allowed schemes HTTP/HTTPS and effective ports 80/443; GET/HEAD/OPTIONS only; exact-origin and submitted-route allowlist; maximum 30 outbound attempts including redirect hops and controls, concurrency 1, no automatic retry; bounded headers, decoded body, redirects, elapsed time, and request body; use fixed configured limits and document actual defaults/units when implemented (the transport currently has 5 s timeout, cooperative 45 s deadline, 262144-byte response maximum and 30 requests). These are not absolute wall-clock guarantees. Reject ambiguous encodings, matrix/dot path variants, query equivalences and noncanonical forms before DNS. All DNS answers must satisfy public-unicast policy; pin selected address, check actual peer before send, preserve Host/SNI and verified TLS, revalidate each redirect; no implicit proxy, credentials or cookie jar. Halt on 401/403/429, Retry-After, defined vendor/WAF/rate signals, unexpected status, incomplete/unsafe response, ambiguity, quota or transport errors. A bounded signature set cannot prove absence of blocks. Do not follow a witness redirect. Local lab isolation must not be an API setting.

## 4. Derived-fact-to-rule mapping — additive proposal

Current rules require `complete is True`, and if `state` is supplied it must equal `completed`; the producer must use false/indeterminate for unperformed, partial, blocked, malformed, unexpected status, TLS failure, truncation and exhausted budget. Current `observe()` returns only outcome and cookie counts; `observe_probe()` returns outcome and two booleans, not the other facts below. Thus the following is an **implementation contract**, not evidence the producer already supplies these facts. Each row uses the exact existing rule key and `observed` polarity. All evidence keys below are **proposed closed enums**, not arbitrary target text. Every fact must be tied to a validated route index, request ordinal, allowed method, recorded UTC instant/date, completion and relevant policy version; route index is an opaque association, not a raw path.

| Source observation after safe parsing | Rule key and existing input | Proposed evidence vocabulary / interpretation |
|---|---|---|
| Successful HTTPS handshake with certificate/hostname verification | `https_tls`: `complete`, `observed=true` only after verified success | `tls_verified`; HTTP, handshake failure, unverified cert or incomplete → `indeterminate`, not a pass |
| Parsed policy under explicitly versioned, conservative header validators | `hsts`, `csp`, `x_content_type_options`, `referrer_policy`, `permissions_policy`: `observed=true` means valid protection, false means missing/invalid under that validator | `policy_valid`, `policy_missing`, `policy_invalid`, `policy_ambiguous`; do not equate presence with validity or claim general security |
| Individual unambiguous Set-Cookie headers, values discarded immediately | `cookie_attributes`: `cookie_count` integer 1..10000, `observed=true` if any missing recommended flag | `cookie_flags_missing`, `cookie_flags_present`, `cookie_ambiguous`, `no_cookies`; zero/ambiguous → incomplete/indeterminate, not conformant. Attribute applicability and SameSite=None/Secure interaction need documented policy |
| Bounded parsed main HTML script `src`, origin comparison only, no fetch | `third_party_scripts`: `observed=true` iff parsed different-origin script | `third_party_script_declared`, `no_third_party_script_seen`, `html_unparseable`; no assertion about script safety |
| Explicit reliable product/package/version declaration | `version`: currently always indeterminate | `component_identity_verified`, `component_identity_ambiguous`, `advisory_unavailable`; no banner-to-version inference; section 6 designs a separate additive advisory assessment |
| Recognized explicit debug indicator or exact known index marker in complete included page | `debug_info`, `directory_index`: boolean `observed` | `debug_indicator_seen`, `directory_index_marker_seen`, `indicator_not_seen`, `parser_ambiguous`; avoid storing snippets, names or personal data |
| One controlled-origin response on the same approved endpoint | `cors`: `origin_tested=true`, `same_endpoint=true`, `kind` and `acao` both `wildcard`/`reflected`/`none`, `credentials` boolean, `observed=(kind != none)` | `cors_wildcard`, `cors_reflected`, `cors_none`, `cors_ambiguous`; invalid/multiple ACAO or inconclusive status → indeterminate; permissiveness alone does not prove sensitive-data access |
| Approved redirect parameter, baseline and mutated request, witness never followed | `redirect`: `probe_performed`, `parameter_authorized`, `witness_checked` true and `destination_followed=false`; existing `observed` alone is insufficient for confirmation | `witness_observed`, `witness_attributed`, `witness_not_observed`, `baseline_inconclusive`; static witness cannot prove causality. Change existing rule before wiring: only causal, comparable baseline plus attributable witness can support narrowly confirmed behavior; otherwise suspected/indeterminate. Negative remains narrowly scoped, preferably indeterminate |
| Approved parameter and inert marker with comparable control | `reflection`: `probe_performed`, `parameter_authorized`, `marker_checked` true; optional context `html_text`/`html_attribute`/`script`/`other`/`unknown` | `marker_reflected`, `marker_not_seen`, `reflection_context_unknown`, `baseline_inconclusive`; reflection is not execution or confirmed XSS; encoded reflection and negative are indeterminate unless specifically supported |

Current rules map completed positive redirect to `confirmed` and some negative probes to `conformant`; this is **unsafe to wire as-is** per the independent review. Narrow or revise those transitions and their tests first. Present `conformant` only as “conformant to the specific completed check”, never a general absence of vulnerability. `attention` is a configuration concern, `suspected` an indication needing verification, `confirmed` only the precise attributable non-destructive behavior; `indeterminate` includes unperformed and failed. Severity must have an explicit rule-specific justification and unknown when not defensible; the current fixed status→severity mapping is not impact-calibrated. Never derive confirmed vulnerability solely from matching an advisory.

## 5. Safe bilingual full-report contract (proposed)

Define one schema-versioned backend envelope shared with TypeScript, rejected on unexpected shape or unknown security-relevant enum, rather than exposing free text from target responses. Proposed `Finding`: `id`, `status`, `severity`, `reason_key`, `evidence_key`, `limitation_key`, `precondition_key`, `recommendation_key`, `severity_reason_key`, `reference_ids[]`, `observation` and `reproduction`. All keys map to locally maintained, complete FR/EN dictionaries; include source-language attribution separately, never machine-translate source advisories. Enforce schema-level allowed key combinations per rule/status; an unknown value must be rejected or explicitly rendered indeterminate, not silently skipped or given a benign default. Use only bounded booleans, enums, validated counts and source identifiers as substitution arguments; validate every argument before output. Escape even allowed values on HTML rendering, use strict CSP, inline local styling only, no external loads, no untrusted markup or Markdown execution.

Example bilingual fixed copy for initial vocabulary (illustrative templates, no assertion of an actual observation):

| Key | Français | English |
|---|---|---|
| `tls_verified` | « TLS et certificat vérifiés pour la connexion observée. » | “TLS and certificate verified for the observed connection.” |
| `cors_reflected` | « L’origine de test contrôlée a été reflétée ; l’accès à des données sensibles n’est pas démontré. » | “The controlled test origin was reflected; sensitive data access is not established.” |
| `marker_reflected` | « Un marqueur inerte a été observé ; cela ne prouve ni XSS ni exécution. » | “An inert marker was observed; this does not prove XSS or execution.” |
| `witness_observed` | « Réponse vers le témoin observée sans suivi ; l’attribution au paramètre reste à établir. » | “A response to the witness was observed without following it; attribution to the parameter remains to be established.” |
| `advisory_candidate` | « Avis en cache potentiellement pertinent ; présence ou exploitabilité non confirmée. » | “A cached advisory may be relevant; presence or exploitability is not confirmed.” |
| `observation_incomplete` | « Contrôle non effectué ou incomplet ; aucune conclusion de protection. » | “Check not performed or incomplete; no conclusion of protection.” |

Fill out equivalent bilingual reason, severity justification, evidence, limits, exploitation preconditions, recommendation and appropriate fixed OWASP/advisory reference for every emitted rule/status combination before calling it full. No invented explanations, severity or source content. References must be fixed allowlisted OWASP IDs/URLs or validated GHSA advisory IDs mapped to the exact canonical URL; display external links as inert text or hardened links, never auto-fetch. No generic OWASP reference should be presented as a check-specific source without review.

A reproducible record needs audit ID (opaque), UTC start/end and observation instant, route **index** associated privately with the operator's submitted allowlist, method, mode, ordered request ordinal/count, check ID/version, completeness/stop reason, baseline/control relationship, named probe kind, and policy/marker version. Fixed witness/marker are identified by version, not reflected response text; parameter names and route paths can themselves contain secrets or personal data, so default report omits them. Reproduction requires the authorized operator's separately held scope/parameter mapping; say so visibly. Record any second observation and budget consumed; never manufacture a control, claim a test occurred, include raw query values or promise identical remote behavior. Dates and identifiers remain literal; only application copy is translated.

Full local printable NIGHTFALL report must include: plain-language summary; privacy-minimized scope and mode; configuration findings; separate suspected vs narrowly confirmed behavior; severity rationale and correction priorities without composite score; minimal typed evidence and reproduction conditions; performed, incomplete and unperformed controls with reasons; source attribution, freshness, and limitations. Render explicit partial/incomplete status on any unfinished check and never advertise certification. Preserve UI navigation/language without stale results; user can export locally only after schema validation. Existing summary export must continue to label itself incomplete until the full contract is actually met. No target response, cookies/values, token, credentials, personal data, raw headers/body, unrestricted URL/query, traceback or sensitive logs in API, persistence or report; the target may still record incoming requests in its own logs beyond application control.

## 6. GHSA: cached lookup and conservative matching (proposed)

Existing P1-C `GhsaService.get(cve_id)` is local-cache only, requires an exact CVE already in the local KEV catalogue and reads `intelligence_*` source `ghsa` with snapshot/view provenance; `fetch` is the separately authorized network collection path and is forbidden in an audit. Cache entries are indexed by CVE, **not package**. A component name alone therefore cannot be passed to `get` or prove coverage. Design a bounded read-only snapshot scan/projection of already validated `source='ghsa'` cached successful advisory payloads across the available local CVE keys, with deduplication by GHSA ID and package/range entry while retaining all contributing CVE/provenance records. Use one explicit SQLite read transaction for data and provenance, no fetch, lease, control-row creation, raw-file write or cache mutation. Validate this actual storage/query shape before implementing; no new precomputed index is assumed. Preserve existing source APIs, legacy rows, status logic and four-source behavior. SQLite read-only WAL may touch auxiliary files; do not promise zero filesystem writes.

Comparison requires all: (1) an independently reliable explicit exact component version; (2) a documented, reviewed mapping from that exact public declaration to an exact GHSA `(ecosystem, package.name)` identity, including case/normalization rules for that ecosystem; (3) cached reviewed advisory and vulnerability entry with valid provenance, non-withdrawn status, complete parse, and supported version/range semantics; (4) tested deterministic comparison. Never infer a package from a loose banner or invent an alias. Start with **no supported ecosystems** until an ecosystem-specific version parser, comparator, canonicalization rules and full supported grammar are approved and tested. For each later enabled ecosystem, declare exact accepted version grammar and all accepted operators (e.g. only a formally specified comparator conjunction if semantics are proven); reject prerelease/build/epoch/wildcard/union/unknown operator, malformed or ambiguous range unless its ecosystem semantics are expressly implemented and tested. Missing/null range, unsupported ecosystem, malformed version, uncertain package identity or ambiguous interpretation → indeterminate, not match or safe. Do not infer a safe version from `first_patched_version` alone or fabricate a fix.

For a valid in-range entry, output `advisory_candidate` / suspected at most, with GHSA ID, linked CVE if present, exact validated package/range where privacy-safe, source URL, source version/date, collection time, provenance hash, state and withdrawal information; a public declaration may not establish installed code or exploitability. Withdrawn advisories remain visible as withdrawn historical records but cannot support a current candidate conclusion or remediation advice. A supported, valid out-of-range comparison means only “this cached entry did not match”, never “no vulnerability”. No match in available cache, successful empty result, not requested, unavailable, stale, retained-after-error, incomplete/partial cache or missing provenance must remain distinct; none proves safety or catalogue completeness. Show both stale and retained-after-error when applicable, preserve source/collection timestamps and GHSA attribution/CC-BY-4.0 and modification notice. Cache is limited to reviewed advisories previously fetched for local KEV CVEs, so even a fresh cache is not comprehensive for the component or ecosystem. Multiple advisories, packages, entries and source CVEs are distinct counts; do not collapse or claim inventory/SBOM coverage. No CISA/NVD/EPSS metric substitutes for a site-specific exposure assessment.
